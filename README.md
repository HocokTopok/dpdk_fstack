# TCP: обычные сокеты и F-Stack + DPDK

## 1. Как устроена система

### Обычный клиент и сервер

Для системы клиент-сервер использовалось два ноутбука. На Mac работал сервер, на Ubuntu —
клиент. Используется **TCP**: он доставляет упорядоченный
поток байтов, обрабатывает подтверждения и повторные передачи. Границы
сообщений задаёт программа символом `!`; один вызов `send()` не обязательно
соответствует одному пакету или одному вызову `recv()`.

Сервер написан на C++ с **Boost.Asio** и использует обычные синхронные
сетевые операции. Boost.Asio вызывает сетевые механизмы ОС; TCP/IP на Mac
обрабатывает ядро macOS. Сервер слушает порт **3333**, принимает одно
подключение и после серии измерений завершается.

Порядок обмена:

1. Клиент создаёт сокет и подключается к IP Mac, порту 3333. TCP устанавливает соединение.
2. После подключения **сервер** отправляет сообщение, например `100!`.
3. Клиент читает байты через `recv()` и возвращает их через `send()`, учитывая частичные отправки.
4. Сервер читает ответ до `!`, проверяет его и переходит к следующему сообщению.

Хотя соединение открывает клиент, в нашем тесте отправку каждого сообщения
инициирует сервер. Клиент выполняет роль эха.

```mermaid
flowchart LR
    S["Сервер C++ / Boost.Asio"] <--> M["TCP/IP и драйвер macOS"]
    M <--> N["Wi-Fi Mac / роутер / Wi-Fi Ubuntu"]
    N <--> L["Драйвер и TCP/IP Linux"]
    L <--> C["Клиент C++ / recv и send"]
```

На Ubuntu обычный путь приёма проходит через сетевую карту, драйвер Linux,
TCP/IP-стек ядра и сокет приложения. Пока данных нет, блокирующий `recv()`
ждёт; после поступления данных ОС возобновляет выполнение клиента.
Скрипт Wi-Fi задаёт `CLIENT_INTERFACE`; клиент использует `SO_BINDTODEVICE`,
поэтому его трафик идёт именно через выбранный Wi-Fi-интерфейс.

### Что такое DPDK

**DPDK** — набор библиотек и драйверов для обработки пакетов в пользовательском
пространстве. В нашем режиме его **PMD** (Poll Mode Driver) работает с очередями
Ethernet-карты, обходя обычный сетевой путь Linux. Приложение активно опрашивает
очереди — это **polling**. Сам DPDK не предоставляет полноценный TCP-сокет:
для TCP нужен дополнительный стек протоколов.

Для пакетов используются заранее организованные пулы буферов (`mbuf`),
а для памяти — hugepages. Это уменьшает накладные расходы на управление памятью.
Карта привязывается к `vfio-pci`; VFIO и IOMMU обеспечивают доступ к устройству
и контролируемое отображение его DMA-памяти. Ядро Linux продолжает работать,
но его обычный TCP/IP-стек не обрабатывает трафик этого DPDK-порта.
[Документация PMD](https://static.dpdk.org/doc/guides/prog_guide/ethdev/ethdev.html),
[память DPDK](https://static.dpdk.org/doc/guides/prog_guide/env_abstraction_layer.html).

### Что такое F-Stack

**F-Stack** добавляет поверх DPDK пользовательский TCP/IP-стек, основанный
на FreeBSD, и интерфейс, похожий на обычные сокеты: `ff_socket`, `ff_connect`,
`ff_recv`, `ff_send`, `ff_close`. TCP-соединение остаётся стандартным,
поэтому сервер Mac не требует специального протокола или DPDK.
[Описание F-Stack](https://github.com/F-Stack/f-stack/blob/dev/README.md).

В `source/client.cpp` сокет неблокирующий. `ff_run()` обрабатывает сетевой
трафик и вызывает нашу функцию `loop()`. Она проверяет подключение,
читает доступные байты и отправляет эхо. Если операция пока невозможна,
возвращает управление циклу, сохраняя буфер и смещение частичной отправки.
Сокет закрывается **внутри цикла**, до остановки `ff_run()`: закрытие TCP
может отправлять пакеты и требует ещё работающих ресурсов DPDK.

```mermaid
flowchart LR
    S["Тот же сервер Mac"] <--> M["TCP/IP macOS / Wi-Fi / роутер"]
    M <--> E["Ethernet-карта Ubuntu"]
    E <--> D["DPDK / PMD / очереди пакетов"]
    D <--> F["F-Stack / TCP/IP FreeBSD"]
    F <--> C["Клиент C++ / ff_recv и ff_send"]
```

### Что измеряется и почему может быть быстрее

На сервере `steady_clock` отмечает время перед отправкой и после получения
полного ответа: **RTT = t₁ − t₀**. Оно включает оба направления сети,
обработку в ОС/стеках и работу клиента. Синхронизация часов ноутбуков не нужна.
Выполняются 100 прогревочных обменов, затем по умолчанию 1000 измерений.
Пауза 10 мс между обменами и запись CSV происходят вне измеряемого интервала.
Оба клиента и сервер используют `TCP_NODELAY`.

DPDK + F-Stack могут уменьшить задержку за счёт обхода обычного сетевого пути
Linux, активного опроса очередей и меньших накладных расходов обработки.
Цена polling — повышенное использование CPU; ускорение зависит от системы.

**Сейчас сравниваются две конфигурации целиком:** обычный клиент Ubuntu по
Wi-Fi и F-Stack по Ethernet; Mac в обоих случаях использует Wi-Fi. Поэтому
меньший RTT нельзя целиком приписывать DPDK. Для проверки именно смены стека
оба клиента нужно запускать через один Ethernet-интерфейс. Этот тест
проверяет задержку коротких сообщений, а не пропускную способность.

Медиана показывает типичную задержку; p95/p99 — пороги, быстрее которых
получены 95%/99% ответов. Для надёжного сравнения полезны несколько
чередующихся серий, поскольку Wi-Fi и фоновые процессы дают редкие скачки.

## 2. Запуск замеров и графика

Все команды — из корня репозитория. На Ubuntu подключить Ethernet и Wi-Fi.
DPDK/F-Stack уже должны быть установлены; скрипты проверяют их и собирают приложения.

### Подготовка

На Mac узнать IP:

```bash
bash scripts/00_network_info.sh
```

В `scripts/settings.sh` на Ubuntu проверить `SERVER_IP`. Между `# //` также
заданы интерфейсы, PCI-адрес, пути установки и число измерений. Экспортированные
переменные имеют приоритет над значениями по умолчанию в этом файле.

### F-Stack + DPDK

Сначала на Mac:

```bash
bash scripts/01_server_mac.sh fstack
```

Когда сервер ждёт подключения, на Ubuntu:

```bash
FSTACK_GDB=0 bash scripts/02_client_fstack_ubuntu.sh
```

Скрипт проверяет кабель, IP и установку, подготавливает память, передаёт карту
DPDK и запускает клиент. После завершения восстанавливает исходный драйвер,
профиль и автоподключение Ethernet, число hugepages и созданные им ресурсы.
Ожидаются `FSTACK_OK`, `RESTORE_OK` на Ubuntu и `SERVER_OK` на Mac.
Один `RESTORE_OK` не подтверждает успешный замер. После `kill -9`/выключения
использовать команду `04_restore_ubuntu.sh` с путём состояния из лога.

### Обычный клиент по Wi-Fi

Сначала на Mac:

```bash
bash scripts/01_server_mac.sh plain_wifi
```

Когда сервер ждёт подключения, на Ubuntu:

```bash
bash scripts/03_client_wifi_ubuntu.sh
```

Ожидаются `PLAIN_WIFI_OK` и `SERVER_OK`. CSV на Mac: `results/<серия>/rtt.csv`;
логи на обоих устройствах: `results/<серия>/terminal.log`. Каждый запуск создаёт новую папку.

### График на Mac

Один раз подготовить Python-окружение:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install matplotlib
```

В `extra/compare_rtt.py` можно менять `PLAIN_CSV`, `FSTACK_CSV` и `OUTPUT_DIR`.
Сейчас выбрана последняя имеющаяся пара из `results/`:

- `plain_wifi_20261109_232306_21290/rtt.csv`;
- `fstack_20261109_232400_21325/rtt.csv`.

```bash
.venv/bin/python extra/compare_rtt.py
```

Результат: один график `results/comparison/rtt_comparison.png`.
Слева показано распределение **всех** RTT, включая скачки; более левая кривая
означает меньшие задержки. Справа — медиана, среднее, p95 и p99. Пути можно
также передать аргументами `--plain`, `--fstack`, `--output`.
